# 各层典型数据单位

## 协议数据单元与封装边界

“报文”“段”“数据报”和“帧”指向不同协议的处理边界。分析抓包或计算传输开销时，先确定题目从哪一层开始计数，再决定哪些首部、尾部和填充需要纳入长度。

| 层次 | 典型单位 | 控制信息或处理对象 |
| --- | --- | --- |
| 应用层 | 报文 | HTTP 请求、DNS 查询、SMTP 命令与邮件内容 |
| 传输层 | TCP 报文段、UDP 用户数据报 | 端口、序号、确认、窗口、检验和等 |
| 网络层 | IP 数据报、分组 | IP 地址、TTL、协议标识、分片信息等 |
| 数据链路层 | 帧 | 成帧、链路地址、类型、帧检验序列等 |
| 物理层 | 比特流 | 比特对应的信号、编码与调制 |

PDU（协议数据单元）是本层与对等实体交换的单位；SDU（服务数据单元）是本层从上层接收的数据；PCI（协议控制信息）是本层添加的控制字段。在不拆分、不聚合的封装模型中：

$$
\mathrm{PDU}_n=\mathrm{SDU}_n+\mathrm{PCI}_n.
$$

这是一种组成关系。例如，一个 UDP 数据报作为 IP 的载荷时，既是传输层 PDU，也是网络层 SDU。若 IP 随后分片，就会形成多个网络层 PDU，不能继续假定两层数据单元一一对应。

“报文”本身不足以定位层次：HTTP 报文属于应用层，ICMP 报文与网络层关联，TCP 报文段属于传输层。“包”常被用作泛称，正式计算应写明协议；“帧”也可能出现在 HTTP/2、QUIC 等协议内部，只有“以太网帧”等限定名称才能确定其层次。

## TCP 字节流与 UDP 报文边界

TCP 向应用提供连续字节流，不保留应用调用 `send()` 的边界。一次写入可能被分段，多次写入可能合并发送；接收端一次 `recv()` 也可能只读到报文的一部分。应用协议需要用长度字段、分隔符或其他规则自行识别边界。

UDP 保留数据报边界，一次正常的数据报发送形成一个 UDP 数据报，首部固定为 $8\,\mathrm{B}$。底层 IP 仍可能将其分片；接收端要在 IP 重组成功后才能交付完整 UDP 数据报。应用提供的接收缓冲区太小时，套接字接口还可能截断数据并报告相应状态。

TCP 首部最小为 $20\,\mathrm{B}$，IPv4 首部最小为 $20\,\mathrm{B}$，二者都可以带选项。TCP 序号以字节为单位；纯确认报文段可以没有应用数据，SYN 和 FIN 各占用一个序号。因此，不能用“报文段个数”直接代替序号增量。

### DNS 与 HTTP 的封装

传统 DNS 的一次 UDP 查询通常按以下方式封装：

```text
DNS 报文 → UDP 用户数据报 → IP 数据报 → 以太网帧
```

UDP 目的端口通常是 `53`。IPv4 的 Protocol 字段以 `17` 标识 UDP，以太网 EtherType 以 `0x0800` 标识 IPv4。它们分别告诉接收端下一步应交给哪个协议处理。DNS 也可以使用 TCP、TLS、HTTPS 等承载，不能由“DNS”推断所有查询都使用 UDP。

HTTP/1.1 的明文报文使用 TCP；HTTPS 还包含 TLS 记录。一个 HTTP 报文、一个 TLS 记录、一个 TCP 报文段之间均无固定的一一对应关系。HTTP/3 使用 QUIC，其数据位于 UDP 载荷内；捕获 UDP 数据报并不意味着其上层缺少可靠传输。

## 帧的逐跳变化

路由器从输入帧中取出 IP 数据报，查表选择下一跳，再按输出链路要求重新封装。在没有 NAT、隧道和分片的普通转发中，源、目的 IP 地址通常不变；TTL 或 Hop Limit 会变化，IPv4 首部检验和也随之更新。

以太网帧的目的 MAC 地址是本链路的下一跳。跨子网访问时，它通常属于默认网关。MAC 地址不跟随 IP 数据报穿越整条路径；中间链路甚至可能不使用以太网。

普通二层交换机按 MAC 地址转发帧，普通路由器按 IP 目的前缀转发分组。设备也可能执行 ACL、NAT 或应用代理，这些功能要另行分析。

## MTU、MSS 与帧长

**链路 MTU**限制该链路一次能够承载的网络层分组长度。常见无额外封装的以太网 MTU 为 $1500\,\mathrm{B}$，这里包含 IP 首部，不包含以太网首部和 FCS。**路径 MTU**是选定路径上各链路 MTU 的最小值。

**TCP MSS**表示接收方愿意接收的最大 TCP 数据长度，不包含 TCP 和 IP 首部。MSS 在 SYN 中按方向通告，实际发送段还受路径 MTU、选项、拥塞窗口等约束。在 IPv4、无 IP/TCP 选项且路径 MTU 为 $1500\,\mathrm{B}$ 时，常见 TCP 数据上限为：

$$
1500-20-20=1460\,\mathrm{B}.
$$

RFC 6691 要求计算通告 MSS 时扣除固定 IP/TCP 首部；发送方实际带有选项时，还要减少数据长度。例如通告 MSS 为 $1460\,\mathrm{B}$、TCP 首部因时间戳及填充变为 $32\,\mathrm{B}$，若仍使用上述路径 MTU，一段最多发送 $1448\,\mathrm{B}$ 数据。

| 长度名称 | 以未加 VLAN 标签的 Ethernet II 为例 |
| --- | --- |
| MAC 首部 | $14\,\mathrm{B}$：目的地址、源地址、类型 |
| MAC 数据字段 | 通常为 $46$ 至 $1500\,\mathrm{B}$，不足时填充 |
| FCS | $4\,\mathrm{B}$ |
| MAC 帧长 | 通常为 $64$ 至 $1518\,\mathrm{B}$，含 FCS |
| 线路上的额外时间 | 前导码和帧起始定界符合计 $8\,\mathrm{B}$；帧间间隔对应 $12\,\mathrm{B}$ 的发送时间 |

帧间间隔是空闲时间，不属于帧的字节内容。VLAN、隧道、巨帧及物理层编码会改变计算条件。题目未要求线路占用或编码开销时，不应自行加入。

!!! question "例题：短 UDP 报文的封装开销"
    应用发送 $10\,\mathrm{B}$ 数据，使用 UDP、无选项 IPv4 和未加 VLAN 标签的 Ethernet II。计算 IP 数据报长、MAC 帧长，以及按 MAC 帧长计算的应用数据占比。若另计前导码和帧间间隔，对应的线路时间占比是多少？忽略物理层编码开销。

    ??? success "参考答案"
        UDP 数据报长为 $10+8=18\,\mathrm{B}$；IP 数据报长为 $18+20=38\,\mathrm{B}$。

        以太网数据字段至少为 $46\,\mathrm{B}$，需要填充 $8\,\mathrm{B}$。MAC 帧长为 $14+46+4=64\,\mathrm{B}$，应用数据占比为 $10/64=15.625\%$。

        再计前导码及帧间间隔，占用相当于 $64+8+12=84\,\mathrm{B}$ 的发送时间，应用数据的时间占比为 $10/84\approx11.90\%$。填充不属于 IP 数据报或 UDP 数据报。

## IPv4 分片与重组

IPv4 数据报超过出口 MTU 时，如果允许分片，可以拆成多个 IP 分片。每片都有自己的 IP 首部；片偏移以 $8\,\mathrm{B}$ 为单位，描述本片数据在**原始 IP 载荷**中的位置。除最后一片外，每片数据长度须为 $8\,\mathrm{B}$ 的整数倍。

无选项、首部长为 $H$、出口 MTU 为 $M$ 时，非末片的最大载荷为：

$$
D=8\left\lfloor\frac{M-H}{8}\right\rfloor.
$$

MF 表示后面是否还有分片；末片的 MF 为零。各片通过标识等字段关联，由最终目的主机重组，普通中间路由器不重组。原始 TCP/UDP 首部属于 IP 载荷，通常仅出现在首片，后续分片不会各复制一份传输层首部。

!!! question "例题：IPv4 分片字段"
    一个总长 $4000\,\mathrm{B}$、首部 $20\,\mathrm{B}$ 的 IPv4 数据报，通过 MTU 为 $1500\,\mathrm{B}$ 的链路，DF 为零且无选项。列出每片总长、片偏移与 MF。

    ??? success "参考答案"
        原始载荷为 $3980\,\mathrm{B}$，非末片最大载荷为 $1480\,\mathrm{B}$，因此分成 $1480$、$1480$、$1020\,\mathrm{B}$ 三段。

        | 分片 | 总长 | 片偏移 | MF |
        | --- | ---: | ---: | ---: |
        | 第一片 | $1500\,\mathrm{B}$ | $0$ | $1$ |
        | 第二片 | $1500\,\mathrm{B}$ | $1480/8=185$ | $1$ |
        | 第三片 | $1040\,\mathrm{B}$ | $2960/8=370$ | $0$ |

        三片总长为 $4040\,\mathrm{B}$，比原数据报多两个 IP 首部。最后一片载荷不必是 $8\,\mathrm{B}$ 的整数倍。

IPv4 的 DF 为一时，中间路由器不能分片，过大的分组通常被丢弃并返回相应 ICMP 差错。IPv6 的中间路由器一律不分片，过大时返回 ICMPv6 Packet Too Big；需要分片时由源节点完成。工程中优先通过路径 MTU 发现和适当的报文大小避免分片，因为任一分片丢失都会影响整个原数据报的重组。

## 抓包结果与线路数据

抓包工具看到的是某个观测点的数据，未必是物理链路上原样出现的帧。分析异常长度或校验和前，需要确认抓包位置和网卡卸载状态。

- **TSO/GSO**：协议栈先提交大块数据，再由网卡或后续软件层分段。发送端抓包可能显示超过 MTU 的“大包”。
- **GRO/LRO**：接收侧把多个分组聚合后交给上层。上层观测到的单元可能大于线上分组。
- **校验和卸载**：发送端抓包时，校验和可能尚未由网卡计算，工具可能标成错误。
- **FCS 与前导码**：网卡通常不会把前导码交给抓包工具，FCS 也经常已被剥除。抓包中的长度可能比 MAC 帧长少 $4\,\mathrm{B}$。

这些现象不能单凭一个抓包字段就判为网络故障。可以在对端或合适的链路观测点复查，结合接口计数器与重传情况判断。Linux 上 `ethtool -k <接口>` 可只读查看卸载能力和状态。

## 长度题的检查顺序

1. 明确已知长度属于应用数据、传输层报文、IP 数据报还是整个帧。
2. 写出每层首部，检查选项、加密、隧道、填充和尾部是否计入。
3. 遇到 MTU 先判断是 TCP 分段还是 IP 分片，分别计算对应边界。
4. 区分数据占比、信道利用率与实际吞吐量。字节占比不能直接包含传播、等待或重传造成的时间损失。

分层职责见[网络分层模型](network-layer-models.md)，窗口与链路利用率计算见[计算机网络常见算法与计算过程](network-algorithms.md)。
