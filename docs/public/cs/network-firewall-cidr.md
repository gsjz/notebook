# 网络基础、防火墙与 CIDR

## TCP 连接、地址变化与 NAT

在同一网络命名空间和 TCP 协议语境下，一条已建立连接通常由源 IP、源端口、目的 IP、目的端口组成的四元组标识。抓包与防火墙中常用的五元组，再加入了传输协议，因此能区分 TCP 和 UDP。

```text
客户端端点                    服务端端点
203.0.113.25:52314      →      198.51.100.10:443
```

端口参与套接字分用，一个服务端监听端口可以承接许多不同四元组的连接。普通 TCP 不提供把已有连接直接迁移到新四元组的机制：客户端换了出口地址，服务端通常无法把新地址发来的报文归入旧连接。应用可能立即得到错误，也可能在下一次读写、保活或重传超时后才发现中断。

家庭网络中的客户端经常先经过网络地址与端口转换（NAPT）：

```text
内侧：192.168.1.23:53124 → 198.51.100.10:443
外侧：203.0.113.25:40001 → 198.51.100.10:443
```

服务端看到的是外侧地址和端口。重新拨号、移动网络切换或 NAT 映射丢失，都可能破坏服务端可见的连接。出口地址变化对已有连接的影响，也取决于是否有隧道、代理或专门的迁移机制维持原来的端点。

NAT 的地址转换与防火墙的访问控制是不同功能。设备经常同时提供二者，未配置映射的外来流量也常无法到达内部主机，但这不构成“NAT 自动提供完整安全策略”的依据。IPv6 无需依靠 IPv4 式地址复用，也仍然需要访问控制。

## 重连与连接迁移

应用重连需要处理两个问题：恢复通信通道，以及确认此前操作的结果。指数退避与随机抖动可以分散重连压力；会话恢复、断点续传和幂等请求标识则用于恢复应用状态。仅仅重新建立 TCP 连接，不会自动恢复上一个连接中的事务。

例如，客户端提交付款后连接断开，可能是请求未到达，也可能是服务端已经提交、响应丢失。此时盲目重发可能重复执行；应用应携带稳定的操作标识，或提供结果查询。

QUIC 使用连接 ID 等机制，使连接能够在符合协议条件时跨地址或端口变化继续存在。新路径需要验证可达性，并重新评估拥塞与路径条件；主动迁移还受握手阶段、对端参数和实现能力约束。连接 ID 不能证明某条新路径必然可用，UDP 被阻断、长时间离线或服务端状态丢失仍会导致失败。

## CIDR 在路由与访问控制中的含义

IPv4 CIDR 前缀 `a.b.c.d/p` 表示前 $p$ 位固定的地址集合，包含：

$$
2^{32-p}
$$

个地址。例如 `/32` 匹配一个地址，`/24` 匹配 $256$ 个地址，`/16` 匹配 $65536$ 个地址，`0.0.0.0/0` 覆盖整个 IPv4 空间。IPv6 对应 `::/0`，IPv4 放行规则不会自然变成 IPv6 规则。

CIDR 可以出现在路由、接口配置和 ACL 中，其含义要由使用位置决定。

| 使用位置 | 前缀描述的对象 | 主要处理规则 |
| --- | --- | --- |
| 路由表 | 一组目的地址 | 通常采用最长前缀匹配，选出下一跳 |
| 接口配置 | 本地接口地址与所属前缀 | 生成相应地址和直连路由，依系统而定 |
| 防火墙 ACL | 来源或目的地址集合 | 还要结合协议、端口、方向、状态和规则顺序 |

**最长前缀优先是普通 IP 路由查表规则，不能直接套到防火墙。** 有些 ACL 按先匹配规则处理，有些云安全组以允许规则并集为准，有些系统还存在优先级、链和默认策略。新增更窄的允许规则，不会自动撤销已经存在的全网允许规则。

`172.16.33.70/20` 规范化后的地址块是 `172.16.32.0/20`，范围为 `172.16.32.0` 至 `172.16.47.255`。前缀边界和掩码的计算见[IP 地址](ip-addressing.md)。ACL 匹配的是整个集合，不扣除普通广播子网中的网络地址和广播地址。

!!! question "例题：路由选择与 ACL 选择"
    路由表含 `203.0.113.0/24` 和 `203.0.113.128/25` 两项，目的地址为 `203.0.113.150`。另有按顺序首条匹配的防火墙，先允许 `0.0.0.0/0` 访问 TCP `22`，后拒绝 `203.0.113.128/25` 访问 TCP `22`。分别判断结果。

    ??? success "参考答案"
        路由查表选择 `/25`，因为它匹配且前缀更长。

        在题目给定的 ACL 规则下，来源 `203.0.113.150` 的 SSH 流量先命中全网允许规则，后面的拒绝规则不起作用。这两个结果分别来自最长前缀匹配与规则顺序，不能相互替代。

## 防火墙策略的组成

一条访问策略至少需要说明方向、地址、协议、端口和动作；状态防火墙还需说明连接状态。云安全组与主机防火墙可能位于不同的网络处理点，即使写出相似的规则，也要核对各自看到的地址是否已经经过 NAT 或代理。

| 服务 | 常见入口 | 面向公网部署时的策略 |
| --- | --- | --- |
| HTTP | `80/tcp` | 公开站点可允许公网访问，用于 HTTP 或重定向等 |
| HTTPS，HTTP/1.1 或 HTTP/2 | `443/tcp` | 公开站点按需求开放 |
| HTTP/3 | 通常为 `443/udp` | 仅在实际部署 QUIC 时放行 |
| SSH | 通常为 `22/tcp` | 优先限定运维来源或覆盖网络 |
| 应用后端 | 如 `3000/tcp` | 按代理与应用拓扑限定来源，不必直接开放公网 |

状态防火墙可以允许已建立连接的返回流量。无状态 ACL 则可能需要分别处理两个方向；不能只照抄服务端熟知端口而忽略客户端临时端口。UDP 没有 TCP 式握手，但连接跟踪系统仍可根据五元组和超时维护临时状态。

不能把 ICMP 全部禁掉来替代精确策略。ICMP 差错用于诊断与路径 MTU 发现，ICMPv6 还承担邻居发现等基础功能。过滤应区分类型、方向和速率，并验证所需控制消息仍然可用。

## UFW 规则的配置与核验

以下示例面向 Ubuntu 主机，示例地址使用保留的文档地址，实施前必须替换为真实运维出口。远程修改时保留当前连接，并准备云控制台或其他独立恢复入口；已建立连接继续存活，不证明新 SSH 连接也被允许。

先检查现有状态和监听端口：

```bash
sudo ufw status verbose
sudo ufw status numbered
sudo ss -lntup
```

在明确现有策略、SSH 实际端口及运维来源后，可以添加所需允许规则。下面限定单个 IPv4 来源访问 SSH，并放行公开 Web 服务：

```bash
sudo ufw allow from 203.0.113.25/32 to any port 22 proto tcp
sudo ufw allow 80/tcp
sudo ufw allow 443/tcp
```

确认无冲突后再设置默认策略并启用：

```bash
sudo ufw default deny incoming
sudo ufw default allow outgoing
sudo ufw enable
sudo ufw status numbered
```

从允许的来源新建第二条 SSH 连接，验证成功后再清理不再需要的旧规则。若原来存在 `22/tcp ALLOW Anywhere`，新增 `/32` 规则不会收紧它；应明确删除或替换那条宽泛允许规则。按编号删除会改变后续编号，不能依照旧清单连续删除。

UFW 的 IPv6 支持受配置影响，应核对 `/etc/default/ufw` 与实际显示的 IPv6 规则，并分别验证 A、AAAA 对应入口。部署 HTTP/3 时，还需明确放行对应 UDP 入口。

### 容器与代理的额外路径

Docker 发布端口可能通过 NAT 和转发链进入容器，与主机进程的输入链不同。仅查看 UFW 入站规则，不能证明容器端口已按预期受限；需要核对 Docker 使用的防火墙后端、端口绑定以及官方规定的转发过滤入口。

同样，应用监听 `127.0.0.1` 只约束其所在网络命名空间。同一台物理主机上的另一个容器，其 `127.0.0.1` 指向自身。设计反向代理到后端的访问规则前，先画清网络命名空间、容器网络及实际连接地址。

## 动态地址与运维入口

来源 IP 白名单适用于稳定、受控的出口。运营商地址池可能包含大量互不相关的用户，把单个来源扩大为整个 `/24` 或 `/16`，相当于授权整个集合，且仍不能保证下一次拨号落在其中。

可以根据部署条件选择以下方式：

| 方式 | 适用条件 | 需要维护的边界 |
| --- | --- | --- |
| 固定出口或堡垒机 | 有集中运维入口 | 入口身份、密钥和访问日志 |
| WireGuard、Tailscale 等覆盖网络 | 设备可加入受控网络 | 设备准入、访问策略与账号安全 |
| 自动更新来源白名单 | 有可靠控制面与 API | 更新凭据、失败恢复与旧规则清理 |
| 较宽的来源前缀 | 前缀确实属于受控组织或可接受集合 | 明确覆盖对象，持续核对归属 |

覆盖网络提供稳定的虚拟寻址和受控入口，但其身份体系、设备密钥及访问策略仍需维护。防火墙放行某地址只证明网络层条件满足，SSH 仍需完成用户认证；业务授权也不会因来源可信而自动成立。

## 分层排查

| 观测结果 | 可以说明什么 | 下一步 |
| --- | --- | --- |
| DNS 返回错误地址 | 入口解析有问题 | 查权威记录、缓存及 TTL |
| TCP 连接超时 | 握手未在期限内完成，原因尚不唯一 | 查路由、过滤、丢包及服务端抓包 |
| TCP 连接被拒绝 | 收到拒绝响应 | 查监听进程、绑定地址和显式拒绝规则 |
| TLS 失败 | 已进入安全协商或校验阶段 | 查域名、证书链、协议配置和时间 |
| HTTP 返回 `403` | 某个 HTTP 节点拒绝请求 | 查代理与应用授权规则 |
| HTTP 返回 `502` | 网关或代理无法得到有效上游响应 | 查上游地址、协议、进程和连接日志 |

一条命令成功只能验证它走过的路径。例如 ICMP Echo 被过滤时，`ping` 失败与 HTTPS 可用可以同时成立；同机回环访问成功，也不能证明公网防火墙和容器发布路径正确。
