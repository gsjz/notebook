# 网络分层模型

## 体系结构、协议与服务

网络体系结构规定层次、各层功能及其协议。它描述通信双方必须遵守的约定，具体功能可以由操作系统、用户态程序或网卡实现。分层的价值在于稳定接口：链路从以太网换成无线网络时，HTTP 请求的含义不需要随之改变。

理解分层时，需要区分三个观察方向。

| 概念 | 观察方向 | 含义 | TCP 中的例子 |
| --- | --- | --- | --- |
| 协议 | 不同节点的对等实体之间 | 通信格式、动作与时序的约定 | 序号、确认、重传与连接建立规则 |
| 服务 | 同一节点的相邻层之间 | 下层向上层提供的可见能力 | 向应用提供可靠、有序的字节流 |
| 接口 | 同一节点内部 | 上层使用下层服务的入口 | 应用通过套接字 API 读写数据 |

对等层之间是**逻辑通信**。发送端 TCP 的数据仍要经过 IP、链路和物理介质，才能到达接收端 TCP。服务只包含上层能够感知和使用的能力；TCP 内部如何计算重传定时器，通常不属于应用可直接调用的服务。

协议的三个要素分别约束：**语法**规定字段格式，**语义**规定字段和操作的含义，**同步或时序**规定事件的先后关系与触发条件。例如，SYN 所在的比特位置属于语法，SYN 请求同步初始序号的含义属于语义，收到 SYN 后如何应答属于时序规则。

## 五层模型与通信范围

五层模型适合把互联网协议与底层传输分别讨论。它是一种教学抽象；实际互联网主机的协议组织通常按 TCP/IP 模型描述。

| 层次 | 主要职责 | 典型数据单位 | 标识与例子 |
| --- | --- | --- | --- |
| 应用层 | 定义应用交换信息的格式与含义 | 应用报文 | HTTP、DNS、SMTP、SSH |
| 传输层 | 为进程提供端到端通信，复用与分用 | TCP 报文段、UDP 用户数据报 | 端口、TCP、UDP |
| 网络层 | 跨网络寻址、路由选择与分组转发 | IP 数据报、分组 | IP 地址、IP、ICMP |
| 数据链路层 | 在相邻节点之间成帧与交付 | 帧 | 以太网、Wi-Fi、MAC 地址 |
| 物理层 | 通过介质传输比特，规定信号与接口特性 | 比特流 | 编码、调制、电气与机械特性 |

这里的通信范围需要结合协议理解。IP 地址一般分配给网络接口，一个接口可以拥有多个地址；端口用于传输层分用，不能把一个端口永远等同于某个固定进程。操作系统还会结合传输协议、本地地址及对端信息选择套接字。

### 各层提供的能力

应用层规定请求、响应、命令与资源的含义。DNS 负责名字解析，HTTP 定义资源访问语义，SMTP 定义邮件提交与传送过程。应用层通过下层服务发送数据，不必直接实现每种物理介质的传输方式。

传输层提供的服务取决于具体协议。TCP 提供可靠、有序的字节流；UDP 保留数据报边界，但自身不提供重传、按序交付、流量控制或拥塞控制。使用 UDP 的应用仍然可以在其上实现这些能力，QUIC 就提供了可靠流、拥塞控制和连接管理。

网络层的 IP 提供无连接、尽最大努力交付。网络可能丢包、乱序或复制分组。**路由选择**计算可用路径，**转发**根据当前转发表处理到达的分组；两者分别属于控制平面和数据平面的典型任务。

数据链路层处理单段链路的成帧、差错检测和交付。以太网通常检测出错误就丢弃帧，Wi-Fi 可以在链路内确认和重传。因此，不能从“属于链路层”直接推出“必然提供可靠交付”。以太网中的 MAC 寻址也不适用于所有点对点链路。

物理层规定比特与信号的对应方式，以及接口、速率等要求。光纤、双绞线和无线空间是承载信号的介质，教材通常把传输介质放在物理层之下讨论。

### 设备与处理层次

| 设备或功能 | 典型判断依据 | 使用条件 |
| --- | --- | --- |
| 中继器、集线器 | 再生或转发信号，属于物理层 | 不按 MAC 地址选择出口 |
| 网桥、二层交换机 | 按目的 MAC 地址转发帧 | 这里限定为二层交换功能 |
| 路由器、三层交换功能 | 按 IP 前缀选择下一跳 | 同时需要链路层与物理层收发 |
| 应用代理、应用网关 | 终止或解析应用协议 | 要按具体功能判断层次 |

“交换机工作在第二层”是对二层交换功能的简化描述。现代设备常同时提供路由、访问控制和隧道功能；网卡也可能卸载 TCP 分段或校验和计算。应试题依据题干给出的典型设备模型，工程排查则依据实际执行的功能。

## OSI、TCP/IP 与五层模型

| OSI 七层 | 五层模型 | TCP/IP 四层 | OSI 中的典型职责 |
| --- | --- | --- | --- |
| 应用层 | 应用层 | 应用层 | 为网络应用提供服务 |
| 表示层 | 应用层 | 应用层 | 表示转换、编码、压缩、加密 |
| 会话层 | 应用层 | 应用层 | 会话管理、对话控制、同步点 |
| 传输层 | 传输层 | 传输层 | 端到端通信 |
| 网络层 | 网络层 | 网际层 | 寻址、路由与转发 |
| 数据链路层 | 数据链路层 | 网络接口层 | 相邻节点交付 |
| 物理层 | 物理层 | 网络接口层 | 比特传输 |

OSI 的表示层与会话层在 TCP/IP 中没有严格对应的独立层。字符编码、压缩和会话管理等功能仍然存在，只是由应用协议、库或其他组件承担。TLS 可以帮助理解表示层中的安全功能，但不能因此认定现实中的 TLS 是一个完整的 OSI 表示层实现。

在常见考研教材的模型比较题中，OSI 网络层可提供面向连接和无连接服务，传输层按面向连接服务描述；TCP/IP 网际层只采用 IP 的无连接服务，传输层则有 TCP 和 UDP。答题时应明确这是教材模型的对比，不把它扩展为所有历史标准和实际协议的绝对限制。

## 封装与逐跳转发

发送方把上层数据交给下层，下层增加本层控制信息；接收方按相反方向解析。在未发生分段、分片、聚合等操作的简化模型下，可写为：

$$
\mathrm{PDU}_n=\mathrm{SDU}_n+\mathrm{PCI}_n.
$$

PDU 是本层协议数据单元，SDU 是本层接收的服务数据单元，PCI 是本层加入的协议控制信息。这里的加号表示组成关系，控制信息可能位于首部或尾部。实际中，一个上层报文可以拆成多个下层单元，因此不能总按“一层一个包”理解封装。长度计算见[各层典型数据单位](network-data-units.md)。

以主机访问远端 HTTP/1.1 服务为例，假定使用 IPv4 和以太网，没有 NAT、隧道或代理：

```text
HTTP 字节 → TCP 报文段 → IP 数据报 → 以太网帧 → 信号
```

主机根据路由表确定下一跳。如果下一跳是默认网关，帧的目的 MAC 地址就是网关接口的 MAC 地址；IP 数据报的目的地址仍是远端服务器。路由器拆除输入链路封装，检查 IP 首部并选择出口，然后用输出链路的封装继续发送。

| 转发时的字段 | 普通 IPv4 路由转发中的变化 |
| --- | --- |
| 源、目的 IP 地址 | 通常不变；NAT、隧道等需要另行分析 |
| TTL | 每经一个路由器至少减一，不能无限循环 |
| IPv4 首部检验和 | 因 TTL 等首部字段变化而更新 |
| 源、目的 MAC 地址 | 由当前以太网链路的发送方和下一跳决定 |
| TCP 端口 | 普通路由转发不改变；NAPT 或代理可能改变 |

ARP 在 IPv4 的以太网链路上解析下一跳 MAC 地址，不会跨路由器查找远端主机的 MAC。ARP 位于 IP 与链路交付的衔接处，教材可能将其归入网际层；判断归层题时应沿用题目模型。IPv6 使用邻居发现协议完成相应工作。

!!! question "例题：跨子网访问的地址字段"
    主机 `192.168.10.8/24` 通过网关 `192.168.10.1` 访问 `198.51.100.20:443`。假定网关不做 NAT，使用 HTTP/2 over TLS over TCP。主机发出的第一跳数据帧中，目的 IP、目的 MAC 和目的端口分别属于谁？网关转发时必须读取 HTTP 请求吗？

    ??? success "参考答案"
        目的 IP 是 `198.51.100.20`，目的 MAC 是网关接口的 MAC，TCP 目的端口是 `443`。IP 标识最终网络层目的端，MAC 标识当前链路下一跳，端口参与目的端套接字的分用。

        普通路由转发只需处理到网络层，不需要读取 HTTP 请求；请求内容还受到 TLS 加密保护。网关转发时会更新 TTL，并为下一段链路重新封装帧。

!!! question "例题：分层封装效率"
    按 OSI 七层的简化模型，应用数据长 $400\,\mathrm{B}$，除应用层和物理层外的五层各增加 $20\,\mathrm{B}$ 控制信息。假定不分段、不分片、没有其他开销，求应用数据占总长度的比例。

    ??? success "参考答案"
        总长度为 $400+5\times20=500\,\mathrm{B}$，应用数据占比为 $400/500=80\%$。这只是给定封装模型下的字节效率；传播、排队、确认等待和重传会另外影响实际传输速率。物理层编码开销也只有在题目要求时计入。

## 服务性质与端到端保证

面向连接、可靠性和应答机制是不同的分类维度。面向连接说明需要维护连接状态；可靠性说明协议承诺什么交付性质；确认说明接收方对什么事件反馈。仅存在连接或确认，都不足以证明一项应用操作已经成功。

TCP 确认表示字节已到达对端 TCP 接收端，并不证明应用已经读取，更不证明数据库已经提交。转账、邮件投递和文件保存仍需要应用层响应；连接中断后若无法确定操作结果，还需要查询状态或使用幂等请求标识。把保证落实到具体层次，可以避免把“可靠传输”误解为“业务必然完成”。

## 现代协议对分层的使用

HTTP/1.1 和 HTTP/2 的常见 HTTPS 协议栈是 HTTP、TLS、TCP、IP。HTTP/3 则使用 QUIC：QUIC 运行在 UDP 之上，把 TLS 1.3 握手与传输机制结合，并提供多个独立的可靠流。

```text
HTTP/2 → TLS → TCP → IP
HTTP/3 → QUIC（集成 TLS 握手）→ UDP → IP
```

QUIC 部署在用户态并不改变其提供传输服务的功能。UDP 提供了广泛可部署的底层承载，QUIC 在其上维护连接、确认、重传与拥塞状态。这也说明，协议所在的代码位置、下层封装以及对上提供的功能，应分别分析。
